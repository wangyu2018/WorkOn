## 📋 协作协议（对面 agent 必读）

本文件就是 issue 板。**修复方只改「状态」和「修复记录」两个字段，然后 push**，QA 侧有监控自动发现变更并回归验证。

### 状态机

| 状态 | 谁标 | 含义 |
|---|---|---|
| `待修` | QA | 新发现的问题 |
| `修复中` | 修复方 | 认领开工 |
| `待验证` | 修复方 | 修完已 push，附 commit hash 和修复说明 |
| `✅ 已验证` | QA | 回归通过 |
| `❌ 复现仍存` | QA | 回归不过，会在「QA 回执」里写新现象 |
| `不修` | 修复方 | 说明理由即可 |

### 修复方回复格式

在每个 bug 下的「修复记录」追加一行：

```
- [2026-10-15 14:30] 状态→待验证 | commit `abc1234` | 说明：paper 分支补齐 props
```

### QA 回执格式

QA 验证后在「QA 回执」追加一行：

```
- [2026-10-15 15:00] ✅ 已验证 | 拆开态目标块出现、合回可用
```

有新 bug 由 QA 追加为 BUG-N 条目（状态=待修）。**只允许 push 到 gitee main，双方不要在同一行上冲突编辑。**

### 平台字段

- `win` —— Windows 侧发现/可复现（QA 本机验）

## BUG-13 ｜ 上下文会话答非所问（问人生规划回计划内容）

**状态**：`待修`
**平台**：通用
**严重度**：中-高（核心对话体验）

**用户原话**：「我问人生规划，他回复我看计划；问计划，他还回我字在计划里面」

**根因已坐实（2026-10-15 QA 复现）**：

`ai.ts:790` 的 `localAnswer(question, …)` 拿到的 `question` 不是用户原文——是 `send()` 里 `withContext()` 拼过的整串：

```
【当前会话：计划】      ← withContext 注入的前缀，含"计划"关键词
今日计划：
- [planned] xxx

今天天气怎么样         ← 用户真正的问句在末尾
```

`localAnswer` 对这整串跑关键词路由，`/计划|plan|目标/` 先命中前缀里的「计划」→ 返回 `ai.ts:791` 的固定话术「计划详情可以在「计划」页查看…」。**用户问天气回计划就是这么来的**（用户截图实锤，当时 LLM 503 走兜底）。

对照实验：LLM 通的时候同一句「今天天气怎么样」（计划 chip 开着）能正确答出天气——所以这是**兜底路径专属 bug**，且更隐蔽：AI 配置正常时永远暴露不出来。

**修法**（两步都要）：
1. `askWithContext`（`ai.ts:824`）调 `localAnswer` 时传**用户原文**而非 `quoted` 整串——关键词路由只该看用户句，不该匹配注入的上下文数据
2. 兜底应答按 `activeContext` 路由到对应 digest 作答（goals→目标进展摘要 / plans→今日计划 / timeline→轨迹 / reminders→提醒），而不是统一给「墙钟/工作/摸鱼」小结

## BUG-14 ｜ 会话内发消息「凭空消失」——sessions 状态从不刷新

**状态**：`待修`
**平台**：通用
**严重度**：高（会话内追问完全不可见，等于会话功能不可用）

**实测现象**：进入会话 → 输入「不要太远，北京周边就行」→ 回车 → 输入框清空（消息发出去了）→ **会话视图里什么都没有**，连刚发的这条都不显示，AI 回复也不出现。

**根因**（链路已查清）：

1. `AskPane.tsx:348` 会话视图渲染 `active.items`，`active` 来自 `props.sessions`
2. `V10Surface.tsx` 的 `sessions` 状态只在 **mount 时** `listSessions` 装一次（行 150），之后只有改名/删除/新建会更新
3. `send()` 行 337 和 `pushAI` 行 103 都调 `window.api.addSessionItem` 写主进程 DB——**但没人回写 `sessions` 状态**
4. 结果：消息落库了，下次重启能看到，但当前会话视图永远显示旧 items

**修法**（二选一）：

- `addSessionItem` 后乐观更新：`setSessions(list => list.map(x => x.id===activeSessionId ? {...x, items:[...x.items, item]} : x))`（send 里 user 一条、pushAI 里 ai 一条）
- 或 `addSessionItem` 返回更新后的 session 再 setSessions

顺带：`AskPane.tsx:366` 会话内发送时调的 `onAddToSession(-1, active.id)` 是个无意义调用（`chat[-1]` 必为 undefined 直接 return），建议删掉。

**复现**：任意会话 ⋯→进入 → 输入框发消息 → 会话视图无任何变化。

**用户原话**：「应该不叫玻璃，我就是想要左侧跟右侧分开，一个能类似我之前的悬浮窗一样固定在桌面。左侧就一个问答页面，可以最小化或者关闭也行，然后右侧能唤醒出来就行。还有就是能比如左侧是报表页，右侧是会话页，这种布局快速切换」

**拆解成三条**：

### 1. 命名/心智模型
「玻璃拆开」「吸附」「合回」这些词用户 get 不到。用户心智是：**悬浮窗格**（像旧版 widget 一样钉在桌面）。按钮文案建议：「拆成双窗」「左窗置顶」「合回单窗」。

### 2. 左窗可关可藏，右窗独立存活（部分已有）
现状已具备：拆开后 ask/paper 各有 收起⇲（去托盘）、置顶📌、合回✕；托盘有「收起/唤回两块玻璃」。
缺口：没有**彻底关闭单片窗格**的入口（收起只是隐藏到托盘玻璃模式）；单片窗格关掉后主窗应自动退回单窗合并态，而不是留个孤窗。

### 3. 窗格角色可换 —— 核心缺失（⭐ 重点）
用户要的是「**窗格是容器，内容是可插拔的页**」：左窗放报表页、右窗放问答/会话页，且能快速切换每片窗格装什么。
现状：`windows.ts:1261` 窗格 role 写死在 URL（`pane=ask` / `pane=paper`），AskPane/PaperPane 一一绑定，无法换内容。

**落地建议**：给窗格加一个「窗格内容」维度（ask | paper | report | session），每片窗格 header 放个小下拉/轮换钮切换内容；`pane=` 参数改成渲染时动态选择组件而非固定绑定。优先级可放后，但架构上要预留。

## BUG-16 ｜ 浮窗「钉在桌面层」点击无效——attach 成功但被自家自检回滚

**状态**：`待修`
**平台**：win（desktopPin 是 Windows 专属，mac 无此功能）
**严重度**：中

**用户原话**：「小组件的固定，点击没效果」

**实测**：CDP 调 `setSettings({widgetDesktopPin:true})` → 1.5s 后读回 `widgetDesktopPin=false`——开关被静默重置，无任何失败提示。

**日志实锤**（dev-out.log）：

```
[desktopPin] attached but not visibly alive, detaching { nativeOk: true, electronOk: false }
```

**根因**（`desktopPin.ts:258-264`）：`SetParent` 挂到 SHELLDLL_DefView **已经成功**（`IsWindowVisible` native 层=true，窗口其实钉上了），但 `electronLooksAlive` 自检里 `win.isVisible()` 返回 false → 触发 `rollbackAttach` 拆掉 → `applyWidgetDesktopPin`（`windows.ts:1049`）把 setting 重置回 false。

`isVisible()` 为 false 的机理：SetParent 重挂父窗会触发 `WM_SHOWWINDOW(SW_PARENT*)`，Electron 内部的可见性记账被带偏——native 层面窗是可见的（IsWindowVisible=true），Electron 侧 flag 却是 hidden。已排除尺寸原因：当时浮窗 120×36 DIP，过了 `≥40×24` 的阈值。

**修法建议**：

- `electronLooksAlive` 里 `isVisible()` 改成信任 native `IsWindowVisible(child)`（nativeOk 已经查了），Electron flag 不应作为否决项；或加 ~50ms 延迟重试再判
- **失败要吱声**：attach 失败静默重置 setting，用户看到的就是「点了没反应」。应推个通知/toast（「钉桌面失败：xxx」），todoWidget 分支已有 `desktop-pin-result` 回执通道可复用，widget 分支目前连失败回执都没有

**复现**：桌搭页/设置里开「钉在桌面层」开关 → 开关立即回弹关闭。

## BUG-17 ｜ 点上下文 chip 后焦点停在按钮上——打字/回车全落空

**状态**：`待修`
**平台**：通用
**严重度**：高（按用户体感=「输入框死了」，极易触发：点完 chip 直接打字是本能动作）

**用户原话**：「切换计划（chip）以后，在里面输入框输入内容打不出来字，回车输入都无效」

**实测复现**（主窗单窗态，真实鼠标+键盘事件）：

1. 点「轨迹」chip → `document.activeElement` = **BUTTON「轨迹」**（焦点停在按钮上）
2. 此时敲键盘 → 输入框 value 完全不变
3. 按 Enter → 等价于再次点击该 chip → 重复注入「切到『轨迹』会话了」AI 消息（也是 BUG-13 里「回错频道」观感的一部分）

**根因**：`AskPane.tsx` ctx-chip 的 `onClick` 后没有把焦点交还给 `v10-input` textarea。按钮拿焦 → 键盘事件全部落在按钮上。

**修法**：`onSetContext` 处理完 `inputRef.current?.focus()`（或在 AskPane 内 chip 点击后 `document.querySelector('.v10-input')?.focus()`）。同理可顺手给快捷 chips（试试建提醒等）和会话返回按钮也补 focus 回输入框。

**顺带建议**：同上下文 chip 重复点击可加守卫（`if (k === activeContext) return`），避免重复注入「切到…」提示。

**复现**：v10 主窗 → 点任一 ctx chip → 直接打字 → 无反应；按 Enter → chip 被重复触发。

## BUG-18 ｜ 托盘右键菜单：命名混乱 + 透明度只有死档 + 双端风格不统一

**状态**：`待修`
**平台**：通用（win 实测，mac 同代码路径）
**严重度**：低-中（观感/易用性）

**用户原话**：「任务栏图标右键里面的内容可以优化一版，显示的文字入口名字太乱，还有什么显示大小20%不能无极吗，还有好丑，两边风格都保持一致」

**当前菜单树**（tray.ts:66-172）：

```
● 记录中（状态行）
打开 WorkOn / ✦ 生成今日日报 / ✦ 问 AI 搭子
玻璃模式 ▸ 拆开（问/右页 两块玻璃片）/ 合回一面 / 吸附固定排布 / 问玻璃（显示/唤回）/ 右页玻璃（显示/唤回）/ 收起全部玻璃
☑ 悬浮窗 / ☑ 待办小组件 / ☑ 桌宠
悬浮窗细化 ▸ 点击穿过（透到下层窗口）/ 置顶显示 / 100%|70%|40%
待办小组件细化 ▸ 同上
桌宠细化 ▸ 透明度三档
暂停记录 / 设置… / 退出 WorkOn
```

**问题拆解**：

1. **命名体系混乱**——「玻璃模式 / 玻璃片」「悬浮窗」「待办小组件」「桌宠」「细化」五套叫法并存，和 v10 内的「拆开/合回/吸附」、设置页里的「钉桌面/穿透」又对不上。同一个东西多个名字。
2. **透明度只有 100/70/40 三档死档**（`opacityRadios`，`tray.ts:42`）——用户要无极调节。Windows 原生菜单做不了滑块，建议：菜单里放「调节透明度…」跳到设置页滑杆，或加一档「自定义…」；也可以在悬浮窗本体上加滚轮调透明度（hover 滚轮=常见桌面挂件惯例）。
3. **「丑」**——原生托盘菜单确实无法套主题皮肤（tray.ts:6 注释已自知）。能做的：统一命名词典、去掉装饰性符号堆砌（✦/⏸/●混用）、把 9 个玻璃子项收敛成 3 个（拆开|合回|唤回管理）。真想根治风格就做 HTML 自绘托盘弹层（工作量大，建议后置）。
4. **两边风格一致**——托盘叫「玻璃模式」但 v10 里叫「玻璃拆开/吸附」；设置页叫「钉在桌面层」。建议立一个统一词典：窗格（pane）/悬浮窗（widget）/待办（todo）/桌宠（pet），托盘、v10 按钮、设置页三处全部对齐。

**修法优先级**：①统一命名词典（低成本高收益）→ ②透明度入口改「调节…」跳设置页滑杆 → ③收敛玻璃子菜单 → ④（可选后置）HTML 自绘托盘菜单。
